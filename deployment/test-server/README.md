# Тестовый сервер RC Chatwoot

Адрес: https://rc-chatwoot.ru. Сервер: `root@168.113.171.75`.
Первое развёртывание: исходники `develop`, ревизия `d54dec0062b8bfafccc4ad5db798e1c6e657eb80`.

## Устройство стенда

- GitHub Actions проверяет сборку, затем запускает обновление через SSH.
- Сервер получает выбранную ревизию из Git-кэша и собирает `rc-chatwoot:FULL_SHA`
  через `docker/Dockerfile`, используя локальный BuildKit-кэш.
- Rails и Sidekiq используют один образ с тегом ревизии исходников.
- PostgreSQL 16 с pgvector, Redis и файлы приложения хранятся в Docker volumes.
- Caddy принимает запросы на 80/443 и автоматически обновляет HTTPS-сертификат.
- Mailpit принимает тестовые письма. Его интерфейс доступен только через SSH-туннель.
- Регистрация отключена. Первый администратор создаётся до публикации приложения.

Конфигурация на сервере: `/opt/rc-chatwoot/deployment/test-server`.
Файл `.env` содержит отдельные секреты стенда и доступен только root.
Он исключён из Git и контекста Docker-сборки.
Локальная `.env` разработчика на сервер не переносится.

## Управление

```sh
ssh root@168.113.171.75
cd /opt/rc-chatwoot/deployment/test-server
docker compose ps
docker compose logs --tail=100 rails sidekiq
docker compose restart rails sidekiq
```

Пароль первоначального администратора сохранён на сервере:

```sh
ssh root@168.113.171.75 'cat /root/rc-chatwoot-admin.env'
```

После изменения пароля в приложении этот файл не обновляется.

Пока распространяется DNS, приложение доступно через защищённый SSH-туннель:

```sh
ssh -N -L 8080:127.0.0.1:8080 root@168.113.171.75
```

Откройте http://localhost:8080. Порт 8080 на сервере доступен только локально;
Caddy передаёт запросы в Rails с признаком HTTPS. Публичный адрес приложения
остаётся https://rc-chatwoot.ru, поэтому ссылки в письмах и внешние интеграции
требуют готового DNS.

Для просмотра тестовой почты запустите на своём компьютере:

```sh
ssh -N -L 8025:127.0.0.1:8025 root@168.113.171.75
```

Откройте http://localhost:8025. SMTP-доставка наружу не настроена.
Для интеграций используйте отдельные тестовые учётные записи.

## Сборка и автодеплой develop

Разработчик создаёт ветку и PR в `develop`. После слияния `Test Docker Build`
проверяет сборки AMD64 и ARM64 на нативных GitHub runners, включая загрузку
native gems и запуск Node. Результаты зависимостей и сборки сохраняются в
GitHub Actions Cache. Публикация образа в GHCR для тестов и деплоя не требуется.
Ручной `workflow_dispatch` только проверяет сборку выбранной ветки.

Успешная проверка после push в `develop` запускает `Deploy test server`.
Он передаёт серверу SHA коммита, а сервер получает новые Git-объекты, извлекает
исходники в отдельную директорию релиза и собирает образ локально. Большие
Docker-образы и полные архивы исходников при каждом деплое не пересылаются.
Сборка использует локальный кэш; при первом запуске нового Dockerfile может
потребоваться установка зависимостей из их обычных источников.

Выкладки идут последовательно. Новый push не отменяет начавшееся обновление.
Перед запуском проверяется текущий SHA `develop`: устаревшая сборка пропускается.
Уже работающая ревизия повторно не выкладывается. PR и ручные проверки сборки
деплой не запускают. Push напрямую в `develop` запускает ту же цепочку;
рабочий процесс команды — ветка → PR → merge.

До остановки приложения сервер собирает образ, сверяет `/app/.git_sha` и
проверяет PostgreSQL/Redis. Затем останавливает Rails/Sidekiq, сохраняет
согласованную копию БД и файлов в `/opt/rc-chatwoot-backups`, выполняет миграции
и обновляет Rails/Sidekiq. Caddy, PostgreSQL и Redis продолжают работать.
После проверок HTTP, БД, Redis, регистрации Sidekiq и статусов Wappi/MAX
переключается `/opt/rc-chatwoot`. Сообщения для проверки не отправляются.

Ход доставки виден в GitHub → Actions → `Test Docker Build`, затем
`Deploy test server`. Результат также отображается в Environment `test-server`.

`Deploy Check` проверяет Compose и shell-скрипты в PR. Upstream-публикация
в Docker Hub и Heroku review apps запускаются только в `chatwoot/chatwoot`.

## Первичная настройка автодеплоя

Создайте на сервере bare Git-кэш исходников:

```sh
git clone --bare --depth=1 --single-branch --branch develop \
  https://github.com/carboninc/chatwoot.git /opt/rc-chatwoot-source.git
```

Полная загрузка нужна один раз. При медленном соединении кэш можно перенести
из проверенной локальной копии; для работы достаточно текущего коммита,
его деревьев и файлов. Каталог используется только для чтения исходников,
серверные `.env` и данные приложения в него не добавляются.

В GitHub Environment `test-server` разрешите деплой только из ветки `develop`
и добавьте секреты:

- `TEST_SERVER_SSH_KEY` — отдельный приватный Ed25519-ключ для CI.
- `TEST_SERVER_KNOWN_HOSTS` — проверенная запись SSH host key сервера.

Добавьте публичный ключ отдельной строкой в `/root/.ssh/authorized_keys` с
опцией `restrict`, без перенаправления портов, агента и PTY. Ключ даёт root-доступ
для скриптов выкладки; доступ к environment и изменениям workflow оставляйте
у доверенных участников. Приватный ключ в репозиторий не добавляется.

## Ручное обновление и диагностика

Из локального checkout можно запустить тот же серверный процесс:

```sh
deployment/test-server/deploy.sh FULL_COMMIT_SHA
```

Ревизия должна быть доступна в origin. Сборка и выкладка продолжаются в фоне,
независимо от SSH-сессии. Прогресс и результат:

```sh
ssh root@168.113.171.75 'tail -f /opt/rc-chatwoot-releases/FULL_COMMIT_SHA/deploy.log'
ssh root@168.113.171.75 'cat /opt/rc-chatwoot-releases/FULL_COMMIT_SHA/deploy.exit'
```

`deploy.exit` появляется при завершении: `0` означает успех. Серверная
блокировка исключает одновременные сборки и выкладки. Повторный запуск той же
ревизии с существующим логом запрещён, чтобы сохранить результат попытки.

Название Compose-проекта (`rc-chatwoot-test`) и volumes сохраняются. Если ошибка
возникла до миграции, прежние Rails/Sidekiq запускаются снова. После начала
миграции автоматический откат образа не выполняется: проверьте совместимость
схемы или восстановите согласованную копию БД и файлов. Логи ошибки сохраняются
в `startup-failure.log`; ссылка указывает на последний успешный релиз.

Для ручной пересборки в существующем релизе:

```sh
docker compose build rails
```

## DNS и HTTPS

Зона `rc-chatwoot.ru` создана в DNS-хостинге AdminVPS с A-записью
`168.113.171.75`. Name-серверы домена: `ns1.adminvps.ru`, `ns2.adminvps.ru`.
При первом развёртывании домен ещё ожидал начального делегирования в зоне `.ru`.
Проверить распространение DNS можно так:

```sh
dig @ns1.adminvps.ru rc-chatwoot.ru A +short
dig @a.dns.ripn.net rc-chatwoot.ru NS +norecurse
dig @1.1.1.1 rc-chatwoot.ru A +short
```

После появления публичного DNS Caddy повторит получение сертификата
автоматически. Состояние сертификата: `docker compose logs --tail=50 caddy`.
