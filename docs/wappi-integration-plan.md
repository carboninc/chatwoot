# Интеграция Wappi

Статус: WhatsApp MVP реализован в отдельном worktree; локальная проверка выполняется 5 октября 2026 года.

## Цель

Добавить в Chatwoot нативный канал Wappi для общения через WhatsApp, MAX, Telegram User API и Avito. Один профиль Wappi соответствует одному inbox Chatwoot.

Разработка идёт поэтапно: WhatsApp, MAX, Telegram, Avito. Перед production-реализацией WhatsApp проводится короткий spike через API inbox и ngrok.

## Принятые решения

- Использовать отдельный `Channel::Wappi`, а не расширять `Channel::Whatsapp` или `Channel::Telegram`.
- Хранить один профиль Wappi в одном inbox.
- Подключать существующий профиль вручную по `profile_id` и API token.
- Регистрировать webhook автоматически при создании inbox.
- Показывать платформу основным названием и иконкой; провайдера «Wappi» показывать в настройках.
- Сделать канал доступным всем аккаунтам без feature flag.
- Не мигрировать существующие WhatsApp и Telegram inbox.
- Не импортировать сообщения, полученные до подключения webhook.
- Не объединять контакты разных платформ автоматически.
- Синхронизировать сообщения, отправленные с телефона или из Wappi, с пометкой «Отправлено вне Chatwoot».
- Не повторять автоматически отправку после неоднозначного сетевого таймаута.
- Не хранить полный webhook payload.

## Граница WhatsApp MVP

Входит:

- создание и настройка inbox;
- автоматическая установка webhook;
- входящие и исходящие текстовые сообщения;
- изображения, документы, аудио и голосовые сообщения;
- ответы на существующие сообщения;
- статусы `delivered`, `read`, `failed`;
- исходящие сообщения, отправленные вне Chatwoot;
- состояния подключения `online` и `offline`;
- ручная проверка подключения;
- создание нового WhatsApp-диалога по номеру телефона.

Не входит:

- импорт истории;
- группы;
- звонки;
- реакции, опросы, редактирование и удаление сообщений;
- рассылки и шаблоны Meta;
- автоматическое объединение контактов;
- автоматическое восстановление отправки после неоднозначного таймаута.

## Модель данных

Новая таблица `channel_wappi`:

| Поле | Назначение |
| --- | --- |
| `account_id` | Владелец канала |
| `platform` | `whatsapp`, позднее `max`, `telegram`, `avito` |
| `profile_id` | Идентификатор профиля Wappi |
| `api_token` | Зашифрованный токен Wappi |
| `webhook_secret` | Зашифрованный секрет входящих webhook |
| `provider_status` | Последний статус профиля или приложения |
| `status_reason` | Причина отключения |
| `status_checked_at` | Время последней проверки |
| `status_metadata` | Раздельные состояния авторизации профиля и приложения |
| `created_at`, `updated_at` | Служебные даты |

Уникальный индекс: `platform + profile_id`.

`api_token` и `webhook_secret` не возвращаются через API. Администратор получает только признак `api_token_configured`.

## Компоненты backend

### Канал и создание inbox

- `app/models/channel/wappi.rb` — настройки профиля, шифрование секретов, состояние авторизации.
- `app/models/account.rb` — связь `has_many :wappi_channels`.
- `app/models/inbox.rb` — `wappi?`, callback URL и платформенный medium.
- `app/controllers/api/v1/accounts/inboxes_controller.rb` — тип `wappi`, разрешённые параметры и создание канала.
- `app/helpers/api/v1/inboxes_helper.rb` — связь аккаунта с новым каналом.
- `app/views/api/v1/models/_inbox.json.jbuilder` — безопасная конфигурация для интерфейса.

Создание выполняется сервисом. Сервис валидирует профиль, создаёт channel и inbox в транзакции, устанавливает webhook и откатывает запись при ошибке Wappi. Если установка webhook прошла, а локальная транзакция завершилась ошибкой, сервис пытается удалить webhook.

### Клиент Wappi

- `app/services/wappi/client.rb` — HTTP-запросы, таймауты, авторизация и разбор ответов.
- `app/services/wappi/webhook_setup_service.rb` — установка webhook и типов уведомлений.
- `app/services/wappi/webhook_teardown_service.rb` — удаление webhook.
- `app/services/wappi/health_service.rb` — получение состояния профиля.

Префиксы подтверждаются во время spike:

| Платформа | Предварительный префикс |
| --- | --- |
| WhatsApp | `/api` |
| Telegram | `/tapi` |
| MAX | `/maxapi` |
| Avito | Требует документации Wappi |

Клиент различает ошибки авторизации, валидации, ограничения Wappi, сетевой таймаут и ошибку сервера.

### Входящий webhook

Маршрут:

```text
POST /webhooks/wappi/:platform/:profile_id
```

Поток обработки:

1. Контроллер находит канал по `platform + profile_id`.
2. Контроллер сверяет webhook secret в constant time.
3. `profile_id` из payload должен совпасть с каналом.
4. При наличии `file_link` base64 удаляется; без ссылки поддерживаемое медиа переносится в Active Storage до постановки job. Большой body в Redis не попадает.
5. Контроллер ставит `Webhooks::WappiEventsJob` и сразу возвращает `200 OK`.
6. Job приводит поле `messages` к массиву, обрабатывает события по одному и удаляет оставшиеся непривязанные медиаблобы.

Webhook secret приходит в заголовке `Authorization`. API token нельзя передавать в webhook URL.

### Нормализация событий

| Событие Wappi | Действие Chatwoot |
| --- | --- |
| `incoming_message` | Создать входящее сообщение |
| `outgoing_message_phone` | Создать исходящее сообщение с пометкой внешней отправки |
| `outgoing_message_api` с нашим `bot_id` | Связать webhook с существующим сообщением |
| `outgoing_message_api` с неизвестным `bot_id` | Создать внешнее исходящее сообщение |
| `delivery_status` | Обновить доставку, прочтение или ошибку |
| `authorization_status` | Обновить авторизацию профиля |
| `application_status` | Обновить техническое состояние приложения |
| Неизвестный тип | Записать тип и ID в лог, вернуть `200` |

Полный payload не сохраняется. В БД остаются внешние идентификаторы, тип события и метаданные, нужные интерфейсу и диагностике.

### Контакты и диалоги

- Идентичность строится из `platform`, `profile_id` и Wappi user ID.
- `chatId` хранится в `ContactInbox#source_id` и атрибутах диалога.
- Имя и телефон не используются для автоматического объединения контактов.
- Телефон записывается в контакт только при отсутствии конфликта; иначе остаётся в дополнительных атрибутах.
- Один личный `chatId` соответствует одному диалогу inbox.
- Групповые события подтверждаются кодом `200`, но не импортируются.
- Новый диалог разрешён только для WhatsApp по валидному номеру. MAX, Telegram и Avito работают с существующими чатами до отдельного решения.

### Исходящие сообщения

- `app/services/wappi/send_on_wappi_service.rb` наследует `Base::SendOnChannelService`.
- `SendReplyJob::CHANNEL_SERVICES` получает `Channel::Wappi`.
- Текст отправляется методом Wappi для текста.
- Вложения отправляются по подписанному URL Active Storage.
- Текст сообщения становится подписью первого вложения.
- Для нескольких вложений сохраняется массив внешних `message_id` и `task_id`.

Для корреляции Chatwoot передаёт:

```text
bot_id=cw:<message_id>:<attachment_index>
```

Допустимую длину и точное отражение `bot_id` в webhook нужно проверить во время spike.

### Дедупликация и статусы

- Входящее сообщение определяется по `inbox_id + external_message_id`.
- Создание защищается Redis-lock с ключом из платформы, профиля и внешнего ID.
- Повторный webhook после снятия lock проверяет существующий `source_id`.
- Повторный delivery webhook повторно выставляет тот же статус и не создаёт сообщение.
- API echo с нашим `bot_id` обновляет исходное сообщение вместо создания копии.

Предварительное соответствие статусов:

| Wappi | Chatwoot |
| --- | --- |
| `pending` | `sent` |
| `delivered` | `delivered` |
| `read` | `read` |
| `undelivered`, `temporary ban`, `error` | `failed` |

Соответствие уточняется по реальным событиям spike.

### Ошибки

- `401/403` возвращается как отдельная ошибка авторизации при создании, проверке или обновлении канала.
- Ошибка параметров или другой подтверждённый ответ Wappi помечает исходящее сообщение как `failed`.
- Неоднозначный сетевой таймаут не запускает автоматическую повторную отправку.
- После принятия запроса очередь и TTL контролирует Wappi.
- Входящие jobs можно повторять благодаря дедупликации.

## Spike WhatsApp

Spike не меняет production-код. Он должен ответить на вопросы:

1. Как называется заголовок с webhook secret?
2. Может ли `messages` быть объектом и массивом для каждого типа события?
3. Какие поля стабильно идентифицируют профиль, чат, пользователя, сообщение и задачу?
4. Возвращается ли переданный `bot_id` во всех нужных webhook?
5. Как связаны `task_id`, API response, outgoing echo и delivery status?
6. Какие события приходят для сообщения, отправленного с телефона?
7. В каком виде приходят изображения, документы, аудио и голосовые сообщения?
8. Каковы ограничения на размер файла и длину `bot_id`?
9. Что возвращает Wappi при offline, неверном token, rate limit и временном сбое?
10. Поддерживает ли провайдер безопасный идемпотентный повтор запроса?

Порядок проверки:

1. Поднять Chatwoot в отдельном worktree.
2. Открыть локальный endpoint через ngrok или временный webhook collector.
3. Установить webhook и типы уведомлений на тестовом WhatsApp-профиле.
4. Проверить status API.
5. Получить входящие текст и медиа.
6. Отправить текст и медиа через API.
7. Получить API echo и delivery statuses.
8. Отправить сообщение с телефона.
9. Отключить профиль и проверить status webhook.
10. Очистить webhook после проверки.

API token, webhook secret и реальные персональные данные не коммитятся. Диагностические примеры перед сохранением обезличиваются.

### Подтверждённый контракт

Проверено 4 октября 2026 года на тестовом WhatsApp-профиле Wappi:

- status API возвращает `app_status=open`, `authorized=true`, платформу `wz`;
- webhook secret приходит в HTTP-заголовке `Authorization`;
- корневое поле `messages` встречается и как массив, и как объект, поэтому нормализатор всегда приводит его к массиву;
- входящий личный чат содержит legacy `chatId` с суффиксом `@c.us` и отдельный `whatsapp_chat_id` с суффиксом `@lid`;
- для исходящей отправки API принимает `whatsapp_chat_id` (`@lid`), а legacy `chatId` (`@c.us`) отклоняет;
- ответ отправки содержит `message_id`, `task_id` и `uuid`;
- `outgoing_message_api` возвращает переданный `wappi_bot_id`, `id` и `task_id`;
- delivery-события связываются по `id`/`task_id` и приходят в последовательности `pending`, `delivered`, `read`;
- `outgoing_message_phone` содержит `id`, но не содержит `task_id` и `wappi_bot_id`, и должен создаваться как внешнее исходящее сообщение;
- отправка файла по URL возвращает обычные `message_id`/`task_id`; echo содержит тип, caption, имя, MIME type, временный `file_link` и base64 body;
- `bot_id` вида `cw-spike-media-20261004-a1` отражается без изменений;
- запрос с legacy `@c.us` завершился определённой ошибкой валидации до отправки, поэтому его безопасно помечать `failed` без повтора.

Следствие для модели идентичности: канонический routing ID WhatsApp — `whatsapp_chat_id` (`@lid`). Legacy `chatId` (`@c.us`) и телефон сохраняются как дополнительные идентификаторы для поиска и диагностики, но не используются для исходящей отправки.

Следствие для медиа: если Wappi прислал `file_link`, base64 удаляется до постановки webhook job и файл скачивается по ссылке в job. Если ссылки нет, base64 переносится в Active Storage на границе webhook и также не попадает в аргументы очереди.

## Приёмка WhatsApp

1. Администратор создаёт WhatsApp inbox Wappi по `profile_id` и token.
2. Chatwoot проверяет профиль и автоматически устанавливает webhook.
3. При ошибке установки inbox не остаётся в частично настроенном состоянии.
4. Входящий текст создаёт контакт, диалог и одно сообщение.
5. Повтор того же webhook не создаёт дубль.
6. Входящее изображение, документ, аудио или голосовое доступно оператору.
7. Ответ оператора появляется в WhatsApp.
8. API echo не создаёт второе исходящее сообщение.
9. Статусы `delivered`, `read` и `failed` отражаются в Chatwoot.
10. Сообщение с телефона появляется как внешнее исходящее.
11. Отключённый профиль блокирует отправку и показывает причину администратору.
12. После замены token и успешной проверки существующие диалоги продолжают работать.
13. API token и webhook secret отсутствуют в ответах API и логах.
14. Канал доступен всем аккаунтам без feature flag.

## Проверка и Enterprise

До реализации новых автоматических specs требуется отдельное решение: правила репозитория запрещают добавлять их без явного запроса. Обязательная проверка включает существующие релевантные тесты, Ruby/JS lint и ручные end-to-end сценарии через ngrok.

Для каждого изменения core проверяется Enterprise overlay. `Channel::Wappi` не должен наследовать WhatsApp-specific voice, campaign или template поведение. Зашифрованные поля не должны попадать в audit log.
